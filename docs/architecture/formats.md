# Original formats: the `formats` library and `dwx`

What `packages/formats/` reads, how it is organized and what each `apps/dwx` command does. What we know about each format comes from the decomp (`dw_decomp`); the file and
the function that read it are cited so it can be checked. This document contains no game data, only structures.

The rules that do not change ([dependencies](dependency-rules.md), [asset pipeline](assets-pipeline.md),
[legal policy](../legal/assets.md)):

- `formats` only depends on `core`, and only `apps/dwx` uses it. The runtime never reads a PS1 format.
- Extraction goes one way: original → source. The disc is not rebuilt.
- No file from the disc, nor anything derived from it, enters a repository. The tests use fixtures made by the team
  (synthetic discs and each module's `tests/fixtures/`), never cuts from the disc.

## Disc version

- We start with the **US** disc (`SLUS_010.32`), which is the decomp's default version. EU and JP come later: the
  decomp has a file table per version.
- `dwx extract` identifies the version by the SHA-1 of its executable (those of the full images are missing, see
  below). The decomp only has SHA-1s for the executable and the overlays (`config/<ver>/*.yaml`); the list of SHA-1s
  for each data file is generated by us the first time, from a verified disc, and stored in `packages/formats/` as a
  table (only hashes and names).
- The first piece already exists: `dwx verify <file>` computes the SHA-1 of a file and looks it up in the
  `formats/disc` table (`known_releases.cpp`). Only the commercial versions are supported: **US, EU and JP** (the
  original and revision 1). The decomp's other versions (the demo and `jp_bombom`) are left out. Today the table has
  those four executables; **the hashes of the full images are missing** (Redump tracks), which are added from the
  Redump entry or from a verified dump, never by eye.

## Layout of `packages/formats/`

```
formats/
├─ include/dwe/formats/
│  ├─ disc/        image (BIN/CUE, ISO), ISO9660, file table, sector reading
│  ├─ image/       TIM, TIM packs
│  ├─ model/       TMD, MMD, animations, skeletons
│  ├─ map/         MAP, TFS, collision
│  ├─ text/        US Shift-JIS + ASCII, control codes, font
│  ├─ script/      SCN container, opcodes, listing, script warps and conversion to Lua
│  ├─ effect/      EFE
│  ├─ audio/       VHB (VH+VB), packed banks, SEQ
│  ├─ video/       STR (MDEC + XA)
│  └─ exe/         PS-X EXE, executable tables, overlays
├─ src/
└─ tests/
```

Principles:

- **Pure readers.** Each reader receives a `std::span<const std::byte>` and returns its own structure or a
  `core::Result` with the error. They do not open files or know about the disc: this way they are tested with small
  fixtures.
- **Never trust the data.** All offsets and counts are checked against the buffer size. A malformed file gives an
  error, never an out-of-range read.
- **Explicit little-endian.** Reading field by field with a `ByteReader`, never `reinterpret_cast` of structs.
- **Decomp names.** Fields are called as in the decomp; unknown ones, `unknownXX` with their offset.

## The disc

| What | What it is like | Where the original reads it |
|---|---|---|
| Image | BIN/CUE with 2352-byte sectors (mode 2) or 2048-byte ISO | — |
| File system | Standard ISO9660. Folders `CARD`, `CHDAT`, `DOOR`, `ETCDAT`, `ETCHI`, `ETCNA`, `MAP/MAP1..17`, `MOVIE`, `SCN`, `SOUND/VHB`, `STDDAT`, and in the root the overlays `*_REL.BIN`, `MMM.DAT` and the executable | — |
| File table | `FILE_OFFSET_TABLE[819]` in the executable (US: 818 files and the final entry): `{s32 LBA sector, s32 size, char* name}` in disc order; ends with size 0. It is searched by the name without the folder. The STRs count 2336 bytes per sector and `PSX.EXE` is another name for the executable | `src/main/file.c: lookupFileTable, readFile, readFileSectors` |
| Files opened by path | `SCN\DG.SCN`, `ETCHI\EFEDAT.EFE`, `ETCDAT\FEEL_EF.TMD`, `ETCDAT\EX.TIM`, `ETCDAT\EX.TMD` and the STRs are searched with `CdSearchFile`; in the US they are also in the table | `script_interp.c`, `efe.c`, `efe_table.c`, `mov.c` |

`formats/disc` reads the ISO9660 and also validates that the executable's table matches it (details in
[Disc](../formats/disc.md)). The STR videos are read in mode 2 form 2 (2336 bytes per sector), so the image has to be
BIN, not ISO.

**Packs without an index.** Many files are a concatenation of entries at a **fixed sector stride**, with no header or
compression. The stride is in the original's code, not in the file, so `formats` declares it in a table:

| File | Stride | Entries | Index |
|---|---|---|---|
| `CHDAT\ALLTIM.TIM` | 9 sectors (0x4800) | 180 | Digimon type |
| `CARD\CARD.ALL` | 14 sectors (0x7000) | 66 | card id |
| `SOUND\VHB\VBALL.VHB` | 7 sectors | | `DIGIMON_VBALL_SOUND_ID[]` |
| `SOUND\VHB\VLALL.VHB` | 15 sectors | 66 | `DIGIMON_VLALL_SOUND_ID[66]` |
| `SOUND\VHB\FAALL.VHB` | 0x27 sectors | 33 | music font |
| `SOUND\VHB\ESALL.VHB` | variable | 22 | `MAP_SOUND_PARA[22] {u16 sector, u16 sectors}`, both halved |
| `ETCHI\EFEDAT.EFE` | 10 sectors | per technique | technique id |

## Images

- **TIM:** the standard PsyQ format (4/8/16 bits, with or without CLUT). It is extracted to PNG with the palette as
  metadata ([pipeline](assets-pipeline.md)).
- **Stacked TIMs** (`ETCDAT\ETCTIM.BIN`, `STDDAT\STDTIM.BIN`): TIMs one after another, each with its `0x10` magic; the
  list ends at the first word that is not `0x10`. The original computes each block's size with width × height, not
  with the length field: we do the same and warn if they do not match (`utils2.c: loadStackedTIMFile`).
- **ALLTIM and CARD.ALL:** fixed-stride packs (table above) with a TIM at the start of each entry. In ALLTIM the
  original ignores the TIM's VRAM position and uses the model's (`model.c: uploadModelTexture`). Details in
  [TIM and packs](../formats/tim.md).

## Models and animations

- **TMD:** PsyQ standard (`TMDModel {id, flags, nobj, obj[]}`, `include/dw/model.h`). The original rewrites each
  primitive's texture page and CLUT when loading an MMD (`updateTMDTextureData`) because it uploads its texture to
  another place in VRAM. The files already point to the TIM's own position in `ALLTIM.TIM`, so the extractor corrects
  nothing: the UVs are TIM coordinates and the palette row comes from each primitive's CBA
  ([Models](../formats/models.md#mmd)).
- **MMD** (`CHDAT\MMDn\XXXX.MMD`, 180): `u32 offsetTmd; u32 offsetAnimations;` + TMD + animation table. The folder is
  `type / 30` and the 4-letter name comes from `PTR_DIGIMON_FILE_NAMES[180]` (`model.c: loadMMD`).
- **Animations** (`anim.c: startAnimation, tickAnimation`): a `u32[]` table of offsets (0 = no animation). Each one:
  `s16 frames` (bit `0x8000` = there is per-bone scale), the initial pose of each bone except 0 (optional scale,
  rotation and translation, 3 × s16 each) and a stream of `s16` instructions with the type in the high nibble and the
  frame in the low 12 bits:

  | Type | What it does |
  |---|---|
  | `0x0` | Keyframe: bone, divisor and up to 9 channels, which are per-tick velocities and not positions; it chains while bit `0x8000` is set |
  | `0x1` / `0x2` | Loop start / end |
  | `0x3` | Moves a VRAM rectangle (texture animation) |
  | `0x4` | Plays a sound (bank, id) |

  The sound and texture events are exported as animation markers in glTF. Details in
  [Models and animations](../formats/models.md).
- **Skeletons:** `DIGIMON_SKELETONS` → lists of `{s8 object, s8 parent}`. The bone count is in
  `DIGIMON_DATA[type].boneCount`.

## Maps

- **`MAP_ENTRIES[255]`** (16 bytes): name, number of 8- and 4-bit TIMs, flags (`& 0x1F` sound, `& 0x40` fixed time,
  `& 0x80` has NPC), doors, restroom and load name. The path is `\MAP\MAP{id/15+1}\{name}.MAP|.TFS`
  (`map.c: buildMapPath`).
- **`.MAP`:** a table of `u32` offsets to its sections (`map.c: loadMap`):
  1. configuration: camera, 3 lights and ambient, projection, regions and the tile grid (`s32`, −1 = empty);
  2. and 3. the 8- and 4-bit TIMs;
  4. objects: sprites and their animated instances (only if there are images);
  5. entities: warps (6 × 10 `s16`) and NPCs (34 + 8 `s16` each + 3 per waypoint) (`tamer.c`, `overworld.c`);
  6. collision: a 100 × 100 `u8` grid (cells of 100 units); values other than 0 and 0x80 are triggers
     (`map_collision.c`).
- **`.TFS`:** 512-byte CLUTs and 128 × 128 8-bit tiles of the prerendered background (`map.c: readMapTFS`). The words
  the original skips are, in the US files, the background size (`height << 16 | width`) and the position of each tile
  in VRAM (`row * 128 << 16 | column * 64`). Palette 0 = day, 1 = dusk, 2 = night.
- **Related tables:** `DOOR_MAPDATA[24]` (models `DOOR\DOORnn.TMD` and their position), `TOILET_DATA`,
  `MAP_LIGHT_UPDATE_DATA`.
- **`STDDAT\*.ATR`:** tournament arena collision: the same 100 × 100 `u8` grid as a map's collision section, which the
  original reads as is into `MAP_COLLISION_DATA` (`std_setup.c: STD_loadArenaAssets`,
  `vs_scene.c: VS_loadArenaAssets`). `dwx extract` writes it as `arena/<name>/collision.yaml`.

Output: one PNG of the background per palette, YAML with camera, lights, warps, NPCs and collision (details in
[Maps](../formats/maps.md)).

## Texts

- Two encodings. The strings in the executable and the overlays are one-byte ASCII, and from `0x80` on a two-byte
  Shift-JIS code (`font.c: drawString`, `sjis.c`). The script text (`SCN`) is all full-width Shift-JIS in two-byte
  cells: `showTextbox` copies pairs, so one-byte ASCII does not fit there.
- Character set: rows `0x81`–`0x84` of cp932 with two glyphs specific to the US, `0x8175` = `'` and `0x8176` = `"`
  (cp932 reads them as `「」`). Kanji (only in the Japanese version) come out as a tag.
- The font is in the executable (`font.c`): `CHAR_TO_GLYPH_TABLE` (one code per glyph; 79 in the US), `GLYPH_DATA`
  (24 bytes per glyph: 11 `u16` rows, bits 15–4 = columns with 0 = ink, and a width) and `FONT_CLUT`. The last glyph
  (the US's 78) is the fallback.
- Script text control codes: each one takes **2 bytes** (code and parameter), and `03` takes 4.
  `script_textbox.c: showTextbox` expands `04` number, `05`/`06` tamer and partner names, `07` Digimon,
  `08` technique, `09` item, `0A` money, `0B` merits, `10`/`13`–`15` numeric variables, `11` music and
  `12` tournament; in `04`, `07`–`09`, `11` and `12` the parameter is the **index of a script variable** whose value
  is used. `drawString2` draws `00`–`03`, `0C`/`0E` tabs, `0F` half space and `16`–`1C` fixed columns of the US.
  `0D xx` is a line break, and the text ends at the first `0D` cell followed by a `00` byte (`0D 00 00 00`).
  Whether another page follows depends on whether the next instruction is another `0x1A` (`pageReady`), not on the
  text.
- `02` and `03` have no consumer in the US, do not appear in its data and `drawString2` skips them: they are stored
  as they are (`{raw02:XX}`, `{raw03:XXXXXX}`).
- Output: UTF-8 with the control codes as readable tags (`{color:2}`, `{item:pstat=5}`), lossless in both directions;
  the strings of the executable and the overlays in `text/<language>/<source>.yaml` and the script text in its
  listing. Details in [Texts and font](../formats/texts.md).

## Event scripts

- `SCN\MAPHEAD.SCN` is the global script (0) and stays resident. `SCN\DG.SCN` starts with a table of `u32` offsets in
  bytes per script id (0x2000 bytes are read; the table ends at the entry that equals the file size). Each script
  takes whole sectors, and what follows its code is padding that nobody reads. Script 0 of `DG.SCN` is a copy of
  `MAPHEAD.SCN` that is not loaded.
- Each script: a `u16` with the code offset and `(u16 section, u16 offset)` pairs up to `0xFFFF`
  (`getScriptSection`). Jumps are absolute offsets from the start of the script.
- The opcodes (0x10–0x7E and 0xFB–0xFF) and their arguments are in `include/dw/script.h`; the interpreter is
  `script_interp.c: tickScript`. `formats/script` disassembles them into a list of instructions with typed arguments
  and `dwx extract` writes a YAML listing per script (details in [Event scripts](../formats/scripts.md)).
- **EFE** (`ETCHI\EFEDAT.EFE`): battle effects, one 0x5000-byte slot per technique. A 0x34-byte `EfeFileHeader`
  header with the offsets of its parts: data area, two scripts, work rooms, TMD and TIM. The interpreter
  (`battle_effect.c: BTL_runEFEScript`) has 18 fixed-length opcodes and 97 subopcodes. `formats/effect` decodes it all
  and types the data area following the scripts ([details](../formats/effects.md)).

## Audio

- **VHB** (`SOUND\VHB\*.VHB`): `u32` header + VH (instruments) + VB (ADPCM samples). A sound bank carries
  `{u32 vh = 12; u32 vb; u32 vbEnd}` (`sound.c: readVHBFile`); a music font, `{u32 vh = 16; u32 vb;
  u32 seq; u32 seqEnd}` (`loadMusicFont`).
- **Packed banks:** `FAALL` is 33 fonts of 0x27 sectors, `VLALL` 16 entries of 15 sectors and `VBALL` 71 of 7
  (`readVHBFileSectors`); `ESALL` is split with `MAP_SOUND_PARA`, in units of 1 KB (`loadMapSounds`).
- **VH:** tone block `k` belongs to the `k`-th non-empty program. The frequency of an effect sample comes from the
  `center` and the `shift` of the tone that plays it.
- **Music:** each font's SEQ bank is `u32 offsets[]` (how many = `offsets[0] / 4`) to SEQ data (`playMusic`). SEP is
  not used. The tempo meta goes **without** a length byte (`FF 51 tt tt tt`) and the loop goes in NRPN
  (`CC99 = 20` / `CC6 = loops` at the start, `CC99 = 30` at the end).
- Output: SF2 per bank, MIDI per sequence and WAV per effect sample ([details](../formats/audio.md)).

## Video

- `MOVIE\OP1/OP2/ED2/EDR.STR`: standard STR (MDEC v3, `StHEADER`) with interleaved XA audio, 320 × 176 at 30 fps and
  stereo at 37.8 kHz. The `MOV_MOVIES[4]` table (`mov.c`) gives the first frame and how many are shown. Details in
  [Video](../formats/video.md).
- **Output: YUV4MPEG2 + WAV + YAML**, with no new dependencies. `formats/video` decodes the whole video
  and audio exactly (the MDEC's integer IDCT); the Y4M carries the planes as they come out of the MDEC and the WAV
  the XA's PCM. It takes about 1.1 GB for the four movies, but loses nothing and any tool reads it.
- **Distributed format:** `dwx cook` turns each movie into AV1 + Opus ([Movies](movies.md#cooked-format-and-later-work)).

## The executable and the overlays

- **PS-X EXE** with a 0x800-byte header; in the US the text starts at `0x80090800`, so
  `offset = address − 0x80090000`. The table addresses come from the decomp's `config/us/symbols.txt`; `formats/exe`
  stores only the addresses and sizes per version, never the data.
- **Tables** (US):

  | Table | Entries × size | Structure |
  |---|---|---|
  | `DIGIMON_DATA` | 180 × 0x34 | `DigimonPara`: name, bones, radius, height, type, level, specials, dropped item, techniques |
  | `MOVE_DATA` | 122 × 16 | `Move` |
  | `MOVE_LEARN_CHANCES` | 58 × 3 | chance of learning each technique in battle, per specialty slot |
  | `ITEM_PARA` | 128 × 32 | `Item`: name, price, merits, order, color, whether it can be dropped |
  | `EVOLUTION_REQS` | 63 × 28 | requirements |
  | `EVOLUTION_STATS_GAINS` | 66 × 14 | gains |
  | `EVOLUTION_PATHS` | 62 × 11 | from [5], to [6] |
  | `RAISE_DATA` | 66 × 28 | care |
  | `CARD_DATA`, `TOURNAMENT_SCHEDULE`, `SHOP_MAPS`, medal names, tournaments and music | | |

  The shop has no stock table: an item is sold if its flag `0x180 + id` is set. The tables are extracted to YAML and
  seed the first ruleset (details in [Tables](../formats/tables.md)).
- **Overlays** `*_REL.BIN`: images without relocations that are loaded whole at a fixed address
  (`utils2.c: loadDynamicLibrary`), with an `"MWo1"` header that the loader does not look at. BTL, STD and VS start
  with five embedded files (TIM and TMD) that are exact copies of standalone files. The game tables of FISH, STD, VS
  and TRN are extracted to YAML; the code is not an asset (details in [Overlays](../formats/overlays.md)).

## Saves

- Memory card file `BASLUS-01032DMR` + slot digit, one 8 KB block: `SC` header, title, icon and two copies of
  `SavegamePayload` (main and backup) with their checksum (byte sum). Optional reading in `dwx import-save` to bring a
  save from the original into the engine; it does not exist (neither `dwx import-save` nor a save reader in `formats`).

## What is not known

- 652 bytes of the data area of 33 EFE slots that no script addresses ([details](../formats/effects.md)).

## `apps/dwx`

| Command | Input → output | What it checks |
|---|---|---|
| `dwx verify <file>` | Image or executable → report | SHA-1 and known version |
| `dwx extract <image> [--out content/base] [--force]` | Disc → source | Version and tables from the executable; one extractor per file type (images, tables, maps, arena collision, audio, effects); coverage report with duplicates; the engine mounts the result ([details](../formats/extract.md)) |
| `dwx validate <package>` | Source | Schemas from `content/schemas/`, broken references, each Digimon's contract (skeleton and animations) and that the engine opens each asset, as a mod; `--engine` for the game's own ([details](assets-pipeline.md#dwx-validate)) |
| `dwx cook <package> -o <folder>` | Source → cooked | Package manifest and ids; each PNG decodes, each GLB has a valid header; the cooked package gives the same ids ([details](assets-pipeline.md#cooking)) |
| `dwx pack <package> -o <file.pak>` | Source or cooked → `.pak` with its manifest | Package manifest and ids; the archive is read back whole and each entry matches its SHA-1 ([format](../formats/pak.md)) |

Besides those there are `identify`, `convert-script`, `export-images`, `evolution-guide`, `upscale`, `ui-chart` and
`ui-chart-detail`: they are on the [dwx page](../modules/apps/dwx.md).

- **Coverage report:** for each file on the disc, which extractor read it, what it produced and which parts it did not
  understand (`dwx/coverage.yaml`, [details](../formats/extract.md)).
- **Deterministic:** the same input gives the same output byte for byte, so extractions can be compared in CI with a
  disc that the team has locally.
- **Tests:** each reader is tested with synthetic fixtures generated by the tests themselves (a 2 × 2 TIM, a minimal
  MAP); the full extraction is only tested locally, with each person's disc.
