# Story interpreter

Status: **done, in `main`.** The design was approved by the coordinator (2026-10-21); the decisions are in
[Decisions](#decisions-2026-10-21) and the questions, with their chosen option, at the end ([Q1–Q14](#questions-and-decisions)).
Increments S0–S7 were integrated in order. The game runs the disc's story with this interpreter
(`formats/script`, `packages/game/story`, `packages/session`).

The story interpreter has two halves:

- **The conversion**: `dwx`, when extracting, converts the event scripts (`script/maphead.yaml` and
  `script/dg/NNN.yaml`) into readable Lua, from **the same IR** that the script warps already use
  ([script warps](script-warps.md)).
- **The runtime**: `packages/game/story` runs that Lua (enter the map, talk, step, press, load the map) with the
  original's semantics, and owns the story state (`StoryState`).

Starting rule (the user's direction, binding): **the original's behavior first**, with parity tests (decomp
locators and, later, traces). Every improvement is an explicit, documented and optional delta.

**The decomp is inspiration, not a port** (binding rule, 2026-10-22): "faithful" is the behavior the player
sees. The runtime does not copy the original machine's limits (stack caps, 8- or 16-bit operand widths,
fixed sizes): it sets generous, documented engine guards. Game ranges (caps on variables, items,
stats) are ruleset rules. An access outside the configured state is still a logged error.

The behavior reference is the [event scripts](../reference/scripts.md) sheet.
This document does not repeat it: it cites its sections and adds what the runtime needs.

## Starting point

- **IR** (`formats/script`):
  - `ScriptListing`: instructions with `FlowRole`, typed operands (`Argument`) and `IF` entries (`Condition`).
    Two constructors that give the same result: `readScriptListing(YamlNode)` (the disc's YAML or the one a mod edits) and
    `listingOf(Disassembly)`.
  - `buildScriptFlow` and `structureScript`: a tree without jumps (`if`, loops with `break`, choices, shared
    tails as tail calls, state machine as a last resort).
  - `walkSection` (walk with guards) and `findMapChanges`: used by the static warps.
  - Disc figures (slow structuring test): 222 scripts, 1553 sections, 1550 nested without a state
    machine, 3 with a state machine; 0 `goto`.
- **Lua sandbox** (`packages/engine/script`, in `main`): Lua 5.5 with sol2, per-pack environments, versioned API
  (`ApiRegistry::publish`, scalar values), hooks with a budget per event and per frame, a per-call instruction
  budget (10 M), time (`callDeadline`, 1 s) and memory (64 MiB total, 16 MiB per pack).
- **Session** (`packages/session`): the only place that brings the `packages/game/*` together (rule 4 of
  [dependencies](dependency-rules.md)); fixed 60 Hz tick in `apps/game` (`TickSeconds`).

## 1. The pipeline: from the IR to Lua

### Why Lua and not another form

| Option | In favor | Against |
|---|---|---|
| **Structured Lua generated by `dwx` (chosen)** | Decision already made ("the engine only runs Lua"; "to change an event, a mod edits the Lua"). Readable, debuggable, the mod edits it without tools. Native coroutines for waits. The runtime does not depend on `formats` (rule 2) | The emitter has to be exact; parity is tested separately |
| An IR interpreter in C++ in the engine | Trivial parity by construction | Violates rule 2 (the runtime does not use `formats`) and the user's decision; mods would not edit Lua |
| Custom bytecode | Compact | Unreadable, another format to maintain, no advantage |

The IR interpreter **does exist, but only in the tests**: a reference interpreter over the **block
graph** (not over the structured tree), with a fake world, is the parity oracle of the generated Lua
([tests](#6-increments-and-tests)). It is an extension of the reference walker that
[script warps](script-warps.md#the-representation-formatsscript) already has.

### Steps

```
script/dg/NNN.yaml ─┐                       (contract with dw1fe: does not change)
script/maphead.yaml ┴→ readScriptListing → buildScriptFlow → structureScript ─┐
                                                                              ├→ lua_emitter → story/NNN
                         walkSection / guards (only for the static warps)    ┘               story/NNN_lines
                                                                                              text/<language>/story_NNN.yaml
```

- **Input:** always the YAML (`readScriptListing`), never the bytes. That way the YAML that `dw1fe` or a mod edits is
  converted just like the disc's (2026-10-21 decision: "`dwx` also converts a mod's edited YAML"). The
  disc test already fixes that YAML and disassembly give the same IR.
- **Emitter** (`formats/.../script/lua_emitter`): walks `StructuredScript` and writes one module per script. Each
  command is a call to the `story` API with its named operands; the exact form is in
  [the shape of the Lua](#the-shape-of-the-lua).
- **Line map** (`story/NNN_lines`): for each line of the Lua, the offset of the original command. It is used by
  the parity traces and the error messages ("script/dg/049 0x04c0"), not by execution. Two-column YAML format.
- **Texts:** each `show_textbox` and `set_selection` becomes a key (`story_049.text.0474`), a user decision
  ("dialogs use text keys"). The English text goes to the catalog `text/en/story_049.yaml` of the `base`
  pack; Spanish is [Q4](#q4-story-texts-in-spanish).

### Determinism

- Output stable byte for byte: ordered by offset, without iterating hash tables, fixed format (two-space indentation,
  numbers in decimal except sections and offsets in 4-digit hexadecimal), `\n` line ending.
- Test: converting the same disc twice gives the same bytes; converting the re-read YAML gives the same bytes as
  converting the disassembly.
- No `goto` (project rule): a test walks all the generated Lua of the disc and fails if the word appears.
  The 3 sections that the structurer leaves as a state machine come out as a `while true` loop that dispatches on
  a local variable `state`.

### `ExtractorVersion` and fingerprint

- Writing `story/**` and `text/*/story_*.yaml` changes what `dwx` extracts: **`ExtractorVersion` goes up**
  (`apps/dwx/src/disc_cache.hpp`) in the increment that introduces it, and the cache fingerprint test requires it.
- The emitter declares its own version (`LuaEmitterVersion`), written in the header of each file
  (`-- dwx lua 4: script 49, ...`). Changing the emitter raises both. That way a mod's Lua generated with an old emitter is
  recognized in the log.

### `dwx` and cooking

- `dwx extract` writes the source Lua into the `base` pack, on the user's machine (nothing in git).
- `dwx convert-script <yaml>`: converts a loose YAML, for the mod that edits the YAML with `dw1fe` and wants
  its Lua. Same function as the extraction.
- `cook-content` does **not** compile to bytecode: the `.pak` carries the Lua text. Reason: the sandbox only loads text (loading
  bytecode is a known attack surface and is not portable between Lua versions); the load-time gain
  is negligible (≈ 1 MB of Lua in total). The table in [the assets pipeline](assets-pipeline.md) says
  "Lua text, no bytecode" under cooking ([Q9](#q9-bytecode-when-cooking)).
- `dwx validate`: the pack's Lua compiles (syntax only, in a VM with no API) and each `_lines` covers its Lua.

### Moddability: how a mod changes a section

A mod replaces an asset by its ID (VFS). The unit is **one module per script** with a table of sections, and a
way to replace **a single section** without copying the whole script ([Q2](#q2-unit-of-replacement-for-a-mod)):

- **Whole script:** the mod brings `story/049.lua` and wins over `base` by ID. It already works with the VFS.
- **A section (done, `StoryLuaHost`):** the mod brings `story/patches/<name>.lua`, which returns
  `{ script = 49, sections = { [0x51] = function(original) ... end } }`. The patch's section wins over the module's;
  the other sections of the script remain the module's. The guide for modders is in
  [story API](../modding/story.md#patches-per-section).
  - **Wrapping:** the function receives `original`, the module's section (or `nil` if the module does not have it, or there is no
    module: a patch can add sections). `return original()` is a tail call and the section behaves
    the same as without a patch; calling it and continuing afterwards (`local r = original() ... return r`) puts it one level deeper,
    so a `jump_to_file` inside it returns to the patch when the destination section ends, like a subroutine
    (`FileJump::linkDepth`).
  - **Order:** patches are loaded once, when the first section starts (and again after a `reload_map` of the
    control channel, `StoryLuaHost::reloadScripts`, which discards modules and patches when no section is
    running), from the bottom of the pack stack up
    (and by ID within a pack). If two patches bring the same section the one that is higher up wins and the log
    says so (`story patches: script 49 section 0x0051 runs B; A loses`). The `original` is always the module's section,
    not that of the patch that lost: patches are not chained.
  - **Errors:** a patch that does not load, has no valid `script` or has a section outside 0–65535 is left out with an
    error in the log; the game continues with the module's section. `StoryLuaHost::patchOf` says which patch runs a
    section (for the remote control and the `[mod:story]` debug log).
  - A patch does not carry the `dwx` header (`-- dwx lua N`): a person writes it, not the emitter.

A mod's code runs in **its environment** (sandbox, the pack's memory quota); the `base` Lua runs as
engine code (`PackOrigin::Engine`, `base` layer). The `story` API is the same for both. A patch runs in its
pack's environment and pays for the whole coroutine, including what `original` spends, which keeps the module's environment
(`ScriptModule::coroutine` with a `ModuleFunction`).

## 2. The runtime

### Where it lives

| Piece | Module | What |
|---|---|---|
| `StoryState` | `packages/game/story` | 800 triggers, 256 variables, save, new-game initial state |
| `StoryRunner` | `packages/game/story` | the only interpreter: running coroutine, continuation stack, pending wait, queue of discarded inputs (for the log) |
| `DialogueState` | `packages/game/story` | the original's text box and selection as pure state (page, step mode, owner, cancellation, trigger 49) |
| Ports (`story_ports.hpp` and the `*_orders`/`*_battle` headers) | `packages/game/story` (interfaces) | what the runtime asks of the world: field, partner, inventory, battle, camera, sound, fades |
| Implemented ports | `packages/session` (`story_adapter`) | the glue with `packages/game/field`, `packages/game/partner`, `packages/game/inventory`, `packages/game/battle` (rule 4) |
| `story` API | `packages/session` publishes into `packages/engine/script` | functions of the `story` namespace (semver-versioned) |
| `StoryLuaHost` | `packages/session` (`story_lua`) | the VM's `SectionHost`: script N is the module `story/NNN` of the pack that provides it, section S its `sections[S]`, one coroutine per section; it publishes the part of the `story` API that already works |
| Text box view | `packages/screens` + `packages/engine/ui` | draws `DialogueState`; the original look (9b) dresses it |

`packages/game/story` does not include `packages/game/field` or any other `packages/game/*`: it declares the ports and `packages/session` implements them.
`packages/game/story` does not include `packages/engine/script` either: the runner works with a `SectionHost` interface (start a section,
resume with a value, close) that `packages/session` implements with the VM. That way the runner is tested without Lua.

### Sections and triggers

The entries are those of the sheet ([entry points](../reference/scripts.md#entry-points)). The runtime
exposes them as `StoryRunner::request(Entry)`:

| Entry | Who requests it | Script and section | Locator |
|---|---|---|---|
| Load map (any map change, load game) | session, on entering | `MAPHEAD` section = map index; its `set_script` pushes the load and then runs `0xFE` | `map.c: changeMap`, `script_interp.c: runMapHeadScript` |
| New game | session | `MAPHEAD 0xCC` | `main.c: newGameScene` |
| Talk | field (NPC collision + confirm, or `autotalk`) | the map's script, section = the NPC's script id | `tamer.c: checkMapInteraction` |
| Step on tile 51–79 | field (`Field::cellSections`) | the map's script, section = value; **repeats every frame** while still on top | same |
| Confirm on tile 80–109 | field | same | same |
| Death, item 22, toilet, tournament, fishing | systems | global sections of `MAPHEAD` (`0x4DE`, `0x4DD`, `0x4E2`, `0x4D9`/`0x4DA`, `0x4E4`) | sheet |

Parity rules that the runner applies as they are:

- **A single script at a time.** A request with another one running is **lost** (it is not queued). It is logged in the debug
  log, never in the user's (`tamer.c: checkMapInteraction`).
- **Deferred start:** the first command runs on the next original frame (the story runs before
  the field), except the map load, which takes a first step at once (`runMapHeadScript`), and the section that
  `checkMapInteraction` requests when a scripted warp ends, which runs in that same step (`map.c: scriptTickChangeMap`).
- **End:** `end_section`/`end_script` empty the continuation stack (`returnFromScriptFile`): that is why an
  `end_section` inside a subroutine ends the whole script (in Lua: the subroutine returns the `ENDED` sentinel
  and its caller does `return ENDED`; never `error`).

### The continuation stack

The original's stack mixes subroutine returns (type 1) with engine continuations (types 3 and 4). In Lua the
returns are ordinary function calls; the runner keeps only the continuations:

| Original type | In the runner | When the current section ends |
|---|---|---|
| 1 (`jump_and_link`) | Lua call | — |
| 3 (`set_script`) | `MapLoaded` | prepares the background and runs `0xFE` of the map's script, if it exists |
| 4 (`warp_to`, `teleport`, `section_on_exit`, fleeing) | `RunSection(s)` | yields one frame and runs section `s` of the map's script (`0xFF`: none) |

The stack is not emptied between scripts (an oddity of the original); the runner replicates it (pending continuations are
popped at the next end) and a test fixes it. The original's stack has 8 frames and does not check it; the runner does not
copy that cap. `jump_to_file` with no pending subroutines is a tail jump: the section that jumps is closed and
replaced by the destination one, so a loop of jumps between files (49:0x52 ↔ 199–202:0x33) runs endlessly, as in the
original. From inside a subroutine, the section that jumps waits below the destination one until its
`jump_return`. An engine guard against runaway stops the script with a logged error if the pending subroutines
of all the waiting sections go over **256**; the disc does not go beyond a few.

### Coroutines, frames and waits

- **One coroutine per running script.** The runner creates it when the section starts and resumes it once per
  original frame as long as it is not waiting. Within a frame it runs commands back to back until one yields: the same
  as `tickScript`.
- **Commands that wait yield from C++**: an API function marked as "waiting" ends with
  `lua_yield`, without a continuation (Lua 5.5 allows this for a C function called from Lua inside a coroutine). The
  generated Lua stays flat: `story.show_textbox(...)` reads like a blocking call. A new piece is needed
  in `packages/engine/script`: `ApiRegistry::publishWaiting` ([Q6](#q6-how-a-waiting-command-yields)). Outside a
  story section, a waiting command is a clear Lua error.
- **What a wait returns:** `set_selection` returns the option from 0, or the number of options on cancel (the
  emitter's contract); `start_battle` the
  result (`-1`, `0`, `1`), even though the generated Lua does not use it (the original leaves it in variable 255, and the runtime
  writes it too).
- **Wait types** (from the sheet, [execution model](../reference/scripts.md#execution-model)):

  | Wait | Commands | Ends when |
  |---|---|---|
  | `Frame` | `fadeout_hud`, `move_boulder`, routines 16, 19, 20, 21, 55, opcodes `FC`/`FD`, frame 4 | the next frame |
  | `Textbox` | `show_textbox` | the page is passed (mode 0/1/2 of `set_textbox_mode`) |
  | `Selection` | `set_selection` | chooses or cancels (cancel impossible with trigger 49) |
  | `Delay(n)` | `delay` | `max(n, 1)` frames |
  | `Movement(mask)` | `wait_for_entity` | the requested movement slots free (operand table of the sheet) |
  | `Battle` | `start_battle` | the battle ends (and, after winning without trigger 1, the camera returns) |
  | `Routine(id)` | `call_routine` with a menu or scene | the routine's state machine ends |
  | `MapChange` | `warp_to`, `teleport` | never resumes: the coroutine is closed; the continuation follows |

- **Budget:** each resume is a call with its own budget (`ScriptLimits::instructionsPerResume`,
  200,000 instructions). The disc's scripts are short between waits; the instruction budget is the
  effective limit and is deterministic. The time limit (`resumeDeadline`, 20 ms) remains as a safety net and
  must never decide the result of a test ([5](#5-sandbox-and-api-boundary)).
- **Aborts:** defeat in battle (jumps to `MAPHEAD 0x4DE` without pushing), fleeing (warp to the previous screen with an empty
  frame 4) and a map change make the runner drop the section's coroutine (`ScriptCoroutine`, which closes it when
  destroyed) and continue with whatever continuation applies (`btl.c`, `script_common.c: handleItemLoss`, `scriptInstruction64to7E`).

### Time: the original's frames

- The original runs the logic at **20 frames per second** (`main.c: gameLoop`, `VSync(3)`; sheet on the
  [field](../reference/field.md)). `delay 20` is one second.
- The engine uses a fixed 60 Hz tick. The runner counts **whole ticks** and gives one original frame every 3 ticks
  (`OriginalFrameTicks = 3`, a constant of the `original` ruleset, not of the code). No accumulating seconds in floating
  point: that way a runner frame always lands on the same tick and the traces line up.
- The order within an original frame, like `tickScript`: (1) advance text boxes and the 22 movement slots, (2) advance the
  map change in progress, (3) look at the wait, (4) if not waiting, resume. The place of the story
  step within the session tick follows the order of the original's main loop (see
  [locators](#locators-of-the-loop-and-the-map-change)).
- While the section "freezes" (`scriptPauseGame`, the first command that calls it), the game clock stops, the player
  and the partner do not respond and the camera is released. It is the same contract that `Field` already has for map
  changes (`Field::gameTimeRan`).

### Locators of the loop and the map change

Checked in the decomp (read-only) for this design:

- **Frame order** (`main.c: gameLoop`): input → `processInput` → `updateTournamentRegistration` →
  `tickScript` (only if there is no paused script) → `tickObjects` (tamer, partner, NPCs) → drawing → `VSync(3)`.
  The story runs **before** the field. Consequence: a section that the field requests (talk, step) in the objects
  tick starts on the next frame; the runner does the same by placing its step before `Field`'s in the
  session.
- **No limit of commands per frame** and no frame skipping: if a frame overruns, the game goes slower
  (`gameLoop`). Our budget per step is a safety limit, not a behavior.
- **`delay N`** stores the count and yields; each `tickScript` lowers it (`script_textbox.c: tickTextboxHandling`); on
  reaching 0, the next command runs **in that same frame** (`script_interp.c: tickScript`).
- **`warp_to`/`teleport`** (`scriptInstruction46to58`): push frame 4 with the arrival section (`teleport`:
  none) and cut the script. From the next frame on, `map.c: scriptTickChangeMap`: a 20-frame fade to black,
  map name at frame 10, `changeMap` on reaching 20 and a 20-frame fade in.
  `changeMap` calls `runMapHeadScript`, which runs the whole chain **in the same call** (`set_script` → frame 3
  → `0xFE`) up to the first wait; on popping frame 4, the arrival section gives its first command in that same
  frame. **The fade in overlaps with the arrival section.** Control returns when the script ends
  (movement, player camera and clock).
- **Walking warp** (`tamer.c: tamerTickChangeMap`): no script; 20 of fade, `changeMap`, 20 of fade in and then
  `checkMapInteraction` and the clock.
- **Load game** (`main.c: main`, `initializeLoadedMap`): `runMapHeadScript(saved map)` without frame 4 (the
  script ends with the chain), then positions, exit and a 40-frame fade in.
- **Save** (`main_menu.c: writeSavegame`): 0x17C bytes of `ScriptState` (`script.h`: cards, 800 triggers,
  variables 0–34); variable 0 is saved as 0 if it was 3.
- **Talk** (`tamer.c: checkMapInteraction`): the collision returns an NPC (2–9); it fires if its `autotalk` is 1, or is 0
  and confirm was pressed in this frame, and only with no script running. The section is the NPC's script id, which
  comes from the map's species table (`overworld.c`, the load of the map's species table); `set_digimon` only places it. There is a
  second path from the NPC with `autotalk` (`overworld.c: NPCEntityTickOverworld`). A chat freezes, turning
  the NPC and the tamer toward each other (`scriptPauseGame`).

### Interaction with the rest

- **Dialog:** `DialogueState` replicates `script_textbox.c` (composing the next page while the current one is shown,
  step modes 0/1/2, the speaker's name, `set_textbox_origin`, `set_textbox_size`, canceling with
  trigger 49, the box that stays open until `fadeout_hud`). The control codes only insert values; the
  runner resolves them when composing (`story.var` for numbers and names). The view reads the state; it decides nothing.
- **Camera:** `move_camera_to`, `move_camera_to_entity` and the `_with_camera` variants occupy slot 10. The field's
  camera implements it through a port.
- **NPC and entity movement:** the 22 slots (`tamer.c`, `tickScriptedMovement`) are story state,
  but they move field entities: the runner stores what each slot requests and the field port applies it to the
  entities with each type's rule (walk with animation to the tile, slide in N steps, turn 0x200 per
  frame). Slides share global state in the original (only one at a time): it is replicated.
- **NPCs:** `load_digimon`, `set_digimon` (8 slots, appears if it matches the map's table), `unload_entity`,
  `set_autotalk`.
- **Fades and warps:** `warp_to` uses the field's existing fade (20 frames, map name according to
  variable 6) and the runner's load chain. Routines 45/46 (fade to white) are a new fade of the same
  service.
- **Battle:** `start_battle` with a predefined opponent (variables 250–253) or the NPC that was talked to. The debug
  trigger (`battle_trigger`) sets up a battle with a map NPC; the `StoryBattlePort` port
  generalizes it and returns the result. The consequences (defeat → `0x4DE`, fleeing → warp) belong to the runner.
  Without a predefined opponent, the opponent is the NPC whose section the last touch or chat opened (`TALKED_TO_ENTITY`,
  `StoryAdapter::talkedTo`). After a battle that can be fled (trigger 1 unset) the opponent leaves the map
  until it is reloaded (`battle_main.c`: the NPCs on screen are left with `isOnMap` 0); after a fixed one it
  stays, like mayo00's `species_a`.

### The shape of the Lua

One module per script. **Synthetic** example (not a script from the disc):

```lua
-- dwx lua 4: script 900, generated from script/dg/900.yaml
local story <const> = story
local ENDED <const> = story.ENDED

local sections = {}

local function shared_0120()               -- tail shared by two sections
  story.set_trigger(70)
  return story.warp_to(12, 2, 60)
end

sections[0x0051] = function()              -- step-on tile
  if story.trigger(71) then return ENDED end
  local choice <const> = story.set_selection("story_900.text.0040", 2)
  if choice == 1 then
    story.show_textbox("story_900.text.0062")
    return shared_0120()
  end
  story.fadeout_hud(0)
  return ENDED
end

return sections
```

- One function per section (`sections[0x0051]`), one local function per subroutine and per shared tail.
- The `IF` statements come out of the left→right folding with explicit parentheses (`(a and b) or c`). The tests are
  pure reads (`story.trigger`, `story.var`, `story.stat`, `story.items`, `story.cards`, `story.knows_move`,
  `story.has_condition`, `story.money`): having no short-circuit changes nothing. The comparison operators are those of
  the sheet (unsigned except happiness).
- `warp_to` and `teleport` come out as `return story.warp_to(...)`: the IR already treats them as the end of flow
  (`FlowRole::MapChange`).
- Names: triggers and variables by number in 4a, with a comment if the engine gives them meaning
  (table in the sheet). Symbolic names: [Q3](#q3-names-of-triggers-and-variables).

## 3. State

### `StoryState`
- **Triggers and variables:** the capacity comes from the configuration; the base set has 800 triggers and 256
  variables. Variables are integers and their value range is a ruleset rule (`variableMax`; the original
  stores them in one byte, 0–255). The saved game keeps the original's 35 variables (0–34,
  `main_menu.c: writeSavegame`) and **all** the extra ones of the configured capacity; the rest only live while the game
  runs ([S2 cut 4](#s2-cut-4-decisions)). Cards, the daily inventory and the recycling inventory already have an owner
  (`packages/game/inventory`) and are not duplicated.
- Ranges: in the base set, the valid triggers are **0–799**. In the original, `getTriggerOffset`
  (`script_interp.c`) indexes `ScriptState.triggers[100]` without checking the range, and the bytes that follow in
  `ScriptState` (`script.h`) are the variables, so a trigger ≥ 800 would touch their bits. **The disc never does
  this** (measured on 2026-10-22, below), so the runner does not reproduce that overlap: a trigger outside the configured
  capacity (800 in the base set) is a Lua error logged like the other out-of-range accesses
  ([Q11](#q11-integer-semantics-and-out-of-range-accesses)).
- **Measurement of triggers ≥ 800** (coordinator's decision: measure before deciding). Over the 222 scripts of the
  disc (`script/dg/*.yaml` and `script/maphead.yaml`), every static trigger operand was counted:
  `set_trigger` 1146, `unset_trigger` 227, `spawn_chest` 71, `trigger` conditions of `if` 2009, `compare_date` 0;
  in total **3453 operands, maximum 716, none ≥ 800**. No command takes the trigger number from a variable,
  so there are no unknown operands. The trigger lists in the `data` blocks (`dget.c`, tournaments) are bytes
  that are added to 200 (`TRIGGER_OGRE_FORTRESS_OPENED`) and do not go beyond 453. A disc test in S1 fixes this count so
  that a change in the extraction does not hide it.
- Initial state: with `story_scenes.new_game.chain: original`, everything at zero plus the partner's raised trigger, and
  whatever `MAPHEAD 0xCC` and the `0xFE` of the first map set when the runner runs them. With `seeded`, that of
  `data/new_game_story`, which is also what the static reachability analysis uses.

- **The new day** (`packages/game/story`, `new_day.hpp`, `session::CalendarAdapter`, `calendar` section of the ruleset): each day
  the clock crosses, and once when a game starts (`initializeScripts`), adds 1 to the day counters (variables
  28–31) unless they are 255, and clears bit 0x80 of variable 2 (`script_common.c: dailyPStatTrigger`). The date
  commands can call `CalendarAdapter::startNewDays`. The card shop that the original restocks that day is left
  for after Milestone 1. The original has no seasons.

### Save section (on top of Q8 of script warps (b))

Part (b) of script warps created the `story` section with `StoryState`. The interpreter inherits it without changing its
shape:

```yaml
sections:
  story:
    version: 2
    state:
      triggers: "0000…"     # 800 bits in 200 hexadecimal digits, bit n = trigger n, and then the extras
      variables: [0, 0, …]  # the 35 that the original saved (0–34)
      extra_variables: []   # those the ruleset adds (capacity), all of them
```

Version 2 (#97) adds the ruleset's capacity ([capacity](../modding/story.md#capacity)); a game from
version 1 migrates unchanged.

- **What the runner saves outside a section:** nothing, because the original only
  saves from the save machine (routine 48, inside a script) and on load it runs the `MAPHEAD` chain of the
  saved map. The runner does the same: **the coroutine state is not saved**. The map and its
  place are saved (the session already does it) and on load the "load map" entry is requested.
- **Engine autosave** (`save.md`): if it autosaves with a section running, it saves the state from before
  entering it (the runner freezes it when a section starts). It is an engine delta (the original does not autosave) that
  already exists; it is documented ([Q10](#q10-autosave-with-a-section-running)).
- **Migration:** a game from before `story` does not have the section: `readMissing` sets the new-game state, and
  the triggers that the static analysis gives as "already passed" for the saved map are not inferred (that would be
  inventing history). The game stays in the initial state and the log says so. The section's versions migrate with
  the `SaveSections` chain.

## 5. Sandbox and API boundary

- **`story` namespace**, published by `packages/session` in `packages/engine/script`, semver version of the whole API
  (just one). Scalar functions (the API now only passes scalars) except `warp_to`, which receives a small table:
  if the API stays scalar-only in 4a, `warp_to(screen, exit, section)` with three numbers.
- **Reading and writing state:** `story.trigger(n)`, `story.set_trigger(n)`, `story.var(n)`,
  `story.set_var(n, v)`… A mod uses them like the generated Lua. What a mod **cannot** do: touch the coroutine, the
  continuation stack, or ask for sections outside the entries (a mod that wants to run a section asks for it with
  `story.request(...)`, which honors the "one script at a time" rule).
- **API version:** S2, on publishing `story`, raised `LuaApiVersion` from 1.1.0 to **1.2.0** (it is 1.4.0 today, see the
  [Lua API](../modding/lua-api.md)). The base package does not declare `api:` ([S2 cut 4](#s2-cut-4-decisions)).
- **Neutral names** ("Decided by the coordinator, 2026-10-22"): the `story` functions and the keys a mod sees
  do not name a franchise, console or company. Six commands are renamed on emit (`load_digimon` →
  `load_species_model`…), with a single table and a single list of forbidden words that a test checks; the YAML
  listing and the internal code keep the original names. The text keys are
  `story_<script id, 3 digits>.text.<offset>` and the modules `story/<id>` (`000` = `MAPHEAD.SCN`). Table and
  rules: [story API](../modding/story.md).
- **Budgets:** each resume of a section has its own budget, smaller than that of a generic call,
  in `ScriptLimits` (`instructionsPerResume`, 200,000): the disc does not go beyond a few thousand Lua instructions between
  two waits, and a mod that loops without yielding must be stopped within a frame, not within a second
  ([Q8](#q8-story-budget)). A section stopped by budget ends like an `end_section` (the stack is emptied,
  everything is unfrozen) and is logged with its line map.
- **Determinism:** what decides the result of a section is the instruction budget, never the clock.
  `store_random` uses the session's generator (the game's seed), not `math.random` (which the sandbox provides per
  package). See [Q14](#q14-random-numbers-of-store_random).
- **Tests without a clock bound:** the interpreter's tests measure instructions and frames, never time; the
  sandbox tests that compared the stop time against a clock limit now stop by instructions
  ([Q12](#q12-the-intermittent-failure-of-the-sandbox-tests)).

### S2 cut 4: decisions

Cut 4 is split in two. **4a** (names and extraction) wires nothing into the game; **4b** wires the story into the
session and publishes `story` to the base package's story modules, which is what the original game needs. What
touches mods belongs to phase 5.

**4a**

- **`story.PLAYER`:** the constant for the player character (entity `0xFD`) is `story.PLAYER`; `TAMER` is never
  published. The emitter writes `local PLAYER <const> = story.PLAYER` and the engine constant is `PlayerEntity`. The
  YAML listing keeps the word `tamer`, just as it keeps `set_pstat`: it is the contract with `dw1fe` and does not change.
- **Variables:** the variable commands are called `set_var`, `add_to_var`, `reduce_var` and `copy_var`, and the
  `pstat` operand is called `var` in the Lua comments ([table](../modding/story.md#names)). The listing keeps
  `pstat`.
- `LuaEmitterVersion` went from 2 to 3 and `ExtractorVersion` from 5 to 6.

**4b**

- **One VM per game:** the story's VM belongs to the session (`StoryAdapter` creates it on the first read of the
  rules), separate from the console's. The module cache of `StoryLuaHost` lives as long as the game, and the mounted
  packages do not change during a game, so it never needs to be invalidated. What a mod's story module sees
  belongs to phase 5.
- **Pace:** the ruleset's `story` section gives `ticks_per_frame` (3: the engine ticks at 60 Hz and the original's story
  advances 20 frames per second, `main.c: VSync(3)`), `variable_max` (255) and the keys of
  `StoryFlowRules` from S3 (`frozen_variable`/`frozen_value` 0 and 3, `talk_facing_trigger` 44, `show_name_variable` 6
  with `show_name_by_event`/`always`/`never` 0, 1 and 2). Each session tick is a
  runner tick, even if the game clock is stopped; the random numbers of `store_random` come from the generator
  of the session's systems (`GameSession::random()`), like the original's single `rand()`.
- **`publishApi` failure:** if publishing the `story` API fails, the session is not created: it is a fatal error, not a warning.
- **API version:** `LuaApiVersion` went up to 1.2 when `story` was published. Having the base package declare `api:` is left for phase 5: a
  package without `api:` counts as written for this engine, and declaring it changes the output of `dwx`, which forces raising
  `ExtractorVersion` (the synthetic disc fingerprint test requires it).
- **Saved variables:** the original saves 35 variables. `writeSavegame` copies `0x17C` bytes from the start of
  `ScriptState` (`main_menu.c:5120`; `loadSavegame` copies them back in `main_menu.c:5058`), and `ScriptState`
  (`script.h:158`) is `smth[212]`, `cards[33]`, `triggers[100]` and `pstats[256]`: `0x17C − 345 = 35`. 35 are still
  saved.
- **Variables 35–255 on load:** the original leaves them with whatever was in RAM; the engine sets them to 0, as
  `initializeScripts` leaves them at power-on (`script_interp.c:2208`). It is an optional determinism improvement: it reproduces
  loading on a freshly powered-on original. `ResetUnsavedVariablesOnLoad` (`story_adapter.cpp`) set to `false` goes back to what
  the original does.
- **Emitter version:** `StoryLuaHost` compares the `-- dwx lua N` header of a module with the modules' version
  (`core/story_modules.hpp`, the same one the emitter uses, because the runtime does not depend on `formats`). When creating the
  game it looks at module 0, which the base package always brings; it accepts from `OldestReadable` (3) to `Version` (4), because what
  changed since 3 only adds calls (`story.cancel_closes_choice`) that an old module does not make and without them it
  plays like the original; if it is not in that range or it does not have it, the game does not start, with
  an error asking to extract again ("content extracted by an older dwx; run dwx extract again"). Each module that
  loads afterwards goes through the same check. Without story modules (the tests without a base package) the game starts and
  the log says that no section can run.
- **Entity constants:** `story.PLAYER` and `story.PARTNER` are published together with the first command with an entity that
  gets published, not before.
- **Variable 0 on save:** `writeSavegame` saves variable 0 as 0 if it is 3 and then restores it
  (`main_menu.c:5080`); the engine does the same with the ruleset's `frozen_variable` and `frozen_value`.

### Parity against the original (traces)

Parity against the original is checked with traces: `dwe-game --trace <file>` writes the positions, battles and buttons of each
tick, the original's trace is written in the same format, and `scripts/oracle_compare.py` says where they first diverge
([state trace](../guides/state-trace.md)).

## 7. Risks

- **Timing parity:** 20 Hz over 60 Hz; if the engine changes its tick, the runner keeps counting the original's frames
  with the ruleset's constant.
- **Performance:** 1 MB of Lua; the map script's module is loaded when the map loads (like the original), not all of it.
- **Mods:** a mod that replaces a whole script breaks with every change to the emitter; the per-section patch reduces that.

## Questions and decisions

Each with its options; the first was the recommended one, and the decision is in the table at the top (Q13 went the other way).

### Q1. Form of execution
1. **Generated Lua + reference interpreter only in tests** (recommended): keeps the engine Lua-only and meets rule 2.
2. IR interpreter in the engine: trivial parity, but it violates rule 2 and the user's decision.

### Q2. Unit of replacement for a mod
1. **Module per script + per-section patches** (`story/patches/*.lua`) (recommended): changing one event does not copy the
   whole script.
2. Only the whole script through the VFS: zero new API; fragile against emitter changes.
3. One file per section: replacement through the VFS with no API, but 1553 files and the shared tails end up split.

### Q3. Names of triggers and variables
1. **Number in 4a, with a comment where the engine gives them meaning; symbolic names later, in a table of the
   `game` package** (recommended): it does not invent story names before the GDD.
2. Symbolic names now: more readable, but they are design decisions (visible to modders).

Status (2026-11-06): the story still uses numbers. `story/names` of the `game` package (`StoryNames`,
`packages/game/story`) gives a label, a snake_case id, to the triggers and variables to which the engine already gives
a meaning (medals, player page items, music, routine data), only so that the tools
show them; nothing in the game reads them.

### Q4. Story texts in Spanish
1. **Spanish falls back to the disc's English text** (key without translation → English, marked in the development log)
   (recommended): there is no translation of the original that we can distribute.
2. Translation done by the team in a separate package: content work, not 4a.
3. Block the `es` story routes: contradicts "routes in en and es".

### Q5. Runner pace
1. **The original's frames at 20 Hz, one every 3 whole ticks, a constant in the `original` ruleset** (recommended):
   exact parity and traces that can be aligned.
2. Waits in seconds: simpler, loses the alignment of the traces.

### Q6. How a waiting command yields
1. **`ApiRegistry::publishWaiting` in `packages/engine/script`, which ends with `lua_yield` from C** (recommended): the generated
   Lua stays flat and a mod cannot skip the wait.
2. Lua wrappers in the base that do `coroutine.yield`: it does not touch `packages/engine/script`, but a mod without that wrapper
   cannot wait and the waits end up written twice.
3. The generated Lua yields explicitly after each waiting command: noise on every line.

### Q7. Warps when talking and teleports in the static graph
1. **`via: talk` with the NPC (when the section is the script id of an NPC in the map's table) and the transport's
   `teleport` resolved with the destination table of routine 10** (recommended; additive for the `field/script_warps`
   schema).
2. Leave them as they are (`other`, `teleport` without a destination): the runtime does them the same; the static graph (free
   exploration, minimap) does not see them.

### Q8. Story budget
1. **Own budget per resume (`instructionsPerResume`), smaller than that of a call** (recommended).
2. That of a generic call (10 M instructions, 1 s): a mod in a loop freezes for a second every frame.

### Q9. Bytecode when cooking
1. **Lua text also in the `.pak`** (recommended): a single form, no bytecode loading; fix the asset pipeline's
   table.
2. Bytecode only for engine packages: slightly less loading, another surface and another code path.

### Q10. Autosave with a section running
1. **Save the state from before the section** (recommended): on load, the `MAPHEAD` chain runs again as
   in the original.
2. Do not autosave while a section runs: delays autosaves; closer to the original (which does not autosave).

### Q11. Integer semantics and out-of-range accesses
**Decided (changed once more on 2026-10-22, "the decomp is inspiration"):** operands are integers without the width
of the original machine (neither 8 nor 16 bits, nor operand-width errors). What the player sees of the original is
kept as a rule: the game caps (`add_to_pstat` up to 255, `give_item` up to 99, `reduce_merit` down to 0, the
range of the variables) are ruleset rules, adding and subtracting clamp to the range without overflowing, and comparisons
follow the sheet ([Oddities](../reference/scripts.md#oddities)). An access outside the configured state is a logged
Lua error, and each case is in this list with its locator:

| Case | Locator |
|---|---|
| More than 256 pending subroutines in the waiting sections (engine guard against runaway; the original has 8 unchecked frames) | `script_interp.c: pushScriptStack` |
| `jump_return` with an empty stack or on a frame 3/4 | `script_interp.c: scriptInstruction10to27` |
| Trigger or variable outside the configured capacity (in the original a trigger ≥ 800 would overwrite the variables; the disc does not do this, see [`StoryState`](#storystate)) | `script_interp.c: getTriggerOffset`; `script.h: ScriptState` |
| Sliding (`entity_move_to*`) with 0 steps (division by zero) | `tamer.c: tickEntityMoveTo` |
| `switch` with 0 cases | `script_interp.c: scriptInstruction10to27` |
| `jump_to_file` to a section that does not exist | `script_interp.c: scriptInstruction10to27` |

The disc reaches none of them. The list grows only with new cases of this kind, never with rules.

### Q12. The intermittent failure of the sandbox tests
1. **Separate package in `packages/engine/script`: measure the stop in instructions and leave the clock as a generous ceiling**
   (recommended).
2. Raise the clock bounds: fewer failures, the same problem under more load.
3. Mark them as slow and do not run them in `check-commit`: it hides them.

### Q13. How to reach `miha03`
The decomp gives no path to `miha03` (neither table, nor `warp_to`, nor the transport), nor to `mgen14`–`mgen16`.

Status: option 2; they are documented in the [field sheet](../reference/field.md#map-reach).
1. **Ask the reference rig for a trace with the map change to `miha03`** (recommended): it says which code does it
   (a `changeMap` from code, like death or the return-home item).
2. Accept them as documented reach exceptions (the table that part (b) foresees in `field.md`).

### Q14. Random numbers of `store_random`
The original uses the C library's `rand()` (default seed, no `srand`), shared with battle, tournaments and
field (`math.c: randomLimit`, `script_interp.c`).
1. **The session's generator, with the game's seed, and the same clamping formula `(limit × r) >> 15`**
   (recommended): deterministic and reproducible by seed; the original's exact sequence cannot be matched
   because it depends on everything else that consumes `rand()`.
2. Imitate the original's `rand()` with a stream shared by all the systems: it would only give equal traces if all
   the systems consumed in the same order; it is a change that is not this package's.
